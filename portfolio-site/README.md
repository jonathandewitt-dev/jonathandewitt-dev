# Portfolio Site

This application uses Thunderous web components, static HTML generation, and client-side navigation.

## Stack and commands

Run application commands from `portfolio-site/`. Use pnpm 12.11.2, pinned by `packageManager`,
and preserve `pnpm-lock.yaml`. `vercel.json` explicitly installs with this version: the patched-dependency
lockfile format is incompatible with Vercel's automatic pnpm 9/10 selection. Use `portfolio-site/`
as the Vercel project root so its install override and patch files are included.

| Command                          | Purpose                                                   |
| -------------------------------- | --------------------------------------------------------- |
| `pnpm install --frozen-lockfile` | Install the locked dependencies                           |
| `pnpm dev`                       | Start the Thunderous development server, backed by Vite   |
| `pnpm build`                     | Generate the static site in `dist/`                       |
| `pnpm start`                     | Serve the existing `dist/` with `serve`; build first      |
| `pnpm test`                      | Run unit, Storybook component, and Playwright E2E tests   |
| `pnpm test:unit`                 | Run native Node TypeScript tests with coverage thresholds |
| `pnpm test:components`           | Run Storybook stories in a browser with Vitest            |
| `pnpm test:e2e`                  | Build the site and run desktop/mobile user stories        |
| `pnpm storybook`                 | Develop components in Storybook at port 6006              |
| `pnpm build:storybook`           | Generate the static component explorer                    |
| `pnpm typecheck`                 | Check TypeScript without emitting files                   |
| `pnpm lint`                      | Run ESLint                                                |
| `pnpm format`                    | Check formatting with Prettier                            |

- `thunderous` supplies functional custom elements, HTML/CSS templates, signals, and declarative shadow DOM rendering.
- `thunderous-server` supplies the CLI, HTML layouts and expressions, static generation, TypeScript transpilation,
  and dependency vendorization through import maps. Production output is static; server scripts run during generation.
- `thunderous-csr` uses the browser Navigation API to fetch destination HTML and update matching view elements.

## How the packages work together

1. `thunderous-server` reads pages from the configured `baseDir`, composes layouts, and evaluates server
   scripts and expressions. Isomorphic scripts register `thunderous` components for declarative shadow DOM
   rendering. The build writes HTML, transpiled modules, and vendored dependencies to `outDir`.
2. The browser loads that HTML and its import map. Isomorphic scripts also run in the browser, registering
   the custom elements so their client behavior and signal bindings can initialize.
3. `thunderous-csr` supplies the `View` custom element, registered as `t-view`. It fetches whole destination
   pages generated by `thunderous-server`, updates the document head, and replaces matching views by ID.
   Components within the incoming content initialize through their registered custom element definitions.

Keep these responsibilities separate: page generation belongs to `thunderous-server`, component behavior
belongs to `thunderous`, and navigation between generated pages belongs to `thunderous-csr`. The production
site is static; a server script does not create a request-time API endpoint. Keep pages usable through normal
links and direct loads as well as enhanced navigation.

Use `thunderous.config.ts` for source/output directories, `src/_layout.html` for the document shell,
`src/component-registry.ts` for shared component definitions, and `src/components/` for component code.
Check installed package types and source when an API is unclear; use `package.json` and `pnpm-lock.yaml`
to identify the applicable versions.

## Pages and execution boundaries

Routes follow HTML files: `index.html` serves `/`, and `about/index.html` serves `/about`. New pages should include the shared layout
with a relative `<?layout href="...">` instruction. Its `<slot>` receives the page content. Files and
directories beginning with `_` are excluded from output, so `_layout.html` is not a route.

Keep these script modes distinct:

- `<script server>` runs on the server. Its default-exported object supplies expression data.
  Use `.server.ts` for server-only modules. Values rendered into HTML are public.
- `<script expr>` evaluates during SSR and inserts its result. Use `html` templates for markup.
  `expr:` attributes also evaluate on the server; the layout uses `expr:prominent` for the home page.
- `<script isomorphic>` runs on both server and client. Register components here so they render on the
  server and become interactive in the browser.
- Ordinary scripts run in the browser. Client module scripts and isomorphic scripts have their package
  imports processed for the generated import map.

The layout exports `getMeta()` for its title, pathname, and breadcrumbs. Breadcrumb objects use
`pathname` for the link destination.

Keep browser APIs out of unguarded isomorphic code. Use `clientOnlyCallback` for browser-only work and
lifecycle callbacks for DOM setup/cleanup. Preserve `<t-view id="main-content">` across pages; CSR matches
views by ID. Do not nest views. Use normal links and verify both direct page loads and client navigation.

## Components and styles

Create components with `customElement`, return `html` templates, and register them with `.define()`.
Shared registrations belong in `component-registry.ts`; page-specific registrations can use an isomorphic script.

Component functions run once. Pass signal getters into templates for live bindings, such as `${count}`;
`${count()}` captures a value at render time. Use `derived()` for reactive calculations or conditional
templates and `createEffect()` for side effects.

`attrSignals` exposes string-or-null attribute values. For typed properties, use `propSignals` with the
component's generic type and initialize defaults with `.init()`. Use `null` to remove an attribute and an
empty string to represent its presence. Prefer explicit ternaries for conditional markup.

Define reusable `css` stylesheets outside component functions, then call `adoptStyleSheet(theme)` and adopt
the component stylesheet. Reuse theme tokens and check both light and dark schemes. Shadow-root styles,
slotted content, and document styles have different scopes; global selectors do not style shadow internals.
Preserve semantic elements, keyboard access, and visible focus indicators.

Core `thunderous` HTML templates are not a sanitizer. Check escaping at the actual rendering boundary
before inserting untrusted content; do not assume server expression handling makes all templates safe.

## Application architecture

Three app-level concerns publish their state to the document rather than exposing it to callers. Nothing
imports them in order to be affected by them, so components stay independent of one another.

### Shared state

`src/routes.ts` is the single source for the primary destinations. Their **order is meaningful**: page
transitions travel left or right depending on whether a navigation moves toward the end of the list or back
toward its start. The orbit nav, the header and footer link lists, and the transition direction all read it.

`src/motion.ts` and `src/nav-direction.ts` are started once from `component-registry.ts`, behind a browser
guard because that module is isomorphic. Each publishes two ways:

| Concern       | Attribute on `<html>` | Custom property             | Event on `document` |
| ------------- | --------------------- | --------------------------- | ------------------- |
| Motion        | `data-motion`         | `--motion`, `--motion-play` | `motion:change`     |
| Nav direction | `data-nav-direction`  | `--nav-dir`                 | `nav:direction`     |
| Voyage        | —                     | `--voyage`                  | —                   |

The primary navigation order is: Home → Blog → About Me → My Work → Resume → Contact Me.
`/blog` introduces the future standalone post experiences. `/resume` links readers to the portfolio and explains
how to request private contact details by email. The Blog page uses `x-feature[pending]` for a disabled, clearly labelled placeholder action.
The résumé feature links to the public PDF at `src/assets/Jonathan_Dewitt_Resume_Public.pdf`.

Transitions require an explicit `view-transition-name` attribute in HTML. Supported identities are
`heading`, `content`, `feature`, and `supplement`; the document stylesheet maps these to the corresponding
`page-*` snapshot names. Each identity must occur at most once per rendered page. Mark the outer block
that should move, leaving nested components unmarked. Both snapshot transitions and cold-load entrances
use this opt-in, so cloning or nesting an unmarked component does not create another animated surface.
The supplemental block shares the primary text's animation timing.

### Orbit navigation

`x-orbit-nav` is supplied to the page's `navigation` slot from the layout. It uses the same controls on
mouse and touch devices. Full motion enables the 3D ring; reduced motion retains ordinary flat links.
Mouse movement over the stage smoothly rotates the ring from its current position. Leaving the stage
preserves the visible angle. Hover uses a constant rotation per pixel: forty percent of the frame's width
covers the entire route range, regardless of the starting angle or direction. At either end, reversing
responds immediately without dead travel. Only the active
page and the hovered link receive a highlight. Re-entering starts from the retained position without a jump.
Pressing freezes any hover easing
before hit-testing the item, so a fast click cannot lose its target. Dragging starts from the current angle, stays
within the route range, and preserves its final position across releases. Hover resumes from that position
on the next mouse movement. The nav region owns its touch
gestures; page scrolling remains available outside it.

Activation requires a mouse-down/up or touch-start/end sequence on the same item. Leaving the pressed
item, cancelling the touch, or moving six pixels into a drag permanently cancels that press. Moving
between spans within one link does not cancel it. Keyboard/assistive activation and modified mouse
clicks retain normal link behavior. Keyboard focus centers its destination immediately; drag rotation also updates without easing,
so a pressed target cannot slide away while the browser waits to animate. Mouse focus does not recenter the ring
during a press.

`src/orbit-position.ts` retains the visible angle on the document and centers the destination over
420ms when native navigation starts. Its animation survives CSR replacing the nav host: the incoming
component begins at the current angle and follows the same `orbit:rotation` events. Hover, drag, or
keyboard interaction interrupts centering from the visible position. Reduced motion centers immediately.

Accepted ordinary activations emit the cancelable, composed `nav:request` event with `{ href }`.
`src/navigation-request.ts`, started from the registry, serializes these requests using the Navigation
API's completion promise. This avoids Thunderous CSR's pending-view guard discarding a later destination.
`patches/thunderous-csr@0.0.8.patch` makes that completion include the final HTML validation/fallback; the
upstream detached callback could otherwise replace a newer page with stale content. The patch also emits
`view:transition-ready` from the native snapshot-ready promise, keeping visual motion independent of that
validation delay. Retain the patch until the dependency supplies equivalent lifecycle behavior.
A normal anchor activation is the fallback when the request service is unavailable. The layout supplies
an empty `loading-overlay` slot to `t-view` so its default blocking overlay cannot swallow further nav
presses while a destination loads. The native `::view-transition` overlay also passes pointer events through
to the live nav while content snapshots animate.

`src/orbit-gesture.ts` owns pure drag/activation decisions and is included in the 100% unit coverage scope.
Browser stories exercise native mouse/touch input, repeated drags, cancellation, and delayed navigation
through the public host and events, without opening closed shadow roots.

### Travelling between pages

`--voyage` is the destination's index in `routes`, treated as a coordinate: each page sits at
its own point in space. `x-cosmos` transitions to that position and stays there, so a navigation
carries the viewer somewhere new rather than returning to where it began. Navigating back
retraces the same ground, because position reflects place rather than elapsed time.

The field covers one viewport width per primary route. Star tiles keep their pixel dimensions,
so extending the field preserves density and star size. Each region repeats viewport-sized
nebulae with varied arrangements; the first retains the original composition. Regions overlap
with complementary horizontal masks to blend their clouds across boundaries without hard cuts. Depth carriers
travel 35, 65, and 100vw per route for stars, and 50vw for clouds. Scroll parallax composes
independently, with the foreground moving up to 560px over the page's scroll range.

The deepest layer is `src/assets/orion-nebula.jpg` at 20% opacity, beneath the gradient nebulae
and stars. One photo covers a 140vw by 130vh surface, panning a total of 40vw horizontally and
15vh vertically across the route list. It uses the same voyage timing as the other layers and
stays fixed during scrolling. The oversized surface covers every route without repeating the
photo, so it needs no tiled edges or feathered overlaps.

Voyage begins on `view:transition-ready`, when CSR's content snapshots are ready to animate, rather than at
link activation while the destination is still loading. `navigatesuccess` is also observed for fallback cases. `--nav-duration` is measured from
the active content animations, including their delays (up to 1080ms), so scenery settles with
the last incoming block. `--ease-voyage` combines the departure curve's initial
control point with the arrival curve's final control point, accelerating into travel and
slowing as the incoming content settles.

The layout seeds `--voyage` during static generation so direct loads begin at their destination
without an initial trip from home. The cosmos owns its theme. The page backdrop paints below the fixed cosmos,
while its positioned content paints above it; keep the page wrapper free of a stacking context.

Two things make that work, and both are easy to undo by accident:

- **`x-cosmos` is rendered beside `t-view`, not inside it.** Only the view's children are
  replaced during navigation, so the background survives. Were it rebuilt per page it would
  have no previous position to transition from, and would snap instead of travel.
- **Each depth has its own carrier element.** A star layer already spends both of its transform
  channels — `transform` on ambient drift, `translate` on scroll parallax — so the voyage is
  composed by nesting rather than by a third declaration on the same element.

The custom properties are the important half: they inherit through shadow boundaries, so a component's
internal stylesheet reacts to either concern without importing anything.

### Motion preference

`--motion` multiplies one-shot durations and `--motion-play` pauses ambient ones. A component opts in by
writing `calc(var(--motion) * 200ms)` instead of a literal duration, or `animation-play-state: var(--motion-play)`
for anything infinite. At zero, animations with `fill-mode: both` land on their final frame immediately, so
content still ends up visible rather than frozen mid-flight.

The preference defaults to the OS setting and is overridden by the in-page toggle, which persists to
`localStorage`. An inline script in `_layout.html` applies a stored choice before first paint.

Beware that the `animation` shorthand resets `animation-play-state`, so the longhand has to come after it.

### Page transitions

`thunderous-csr` already wraps its content swap in `document.startViewTransition()`, so the transitions are
pure CSS in `global.css`. The only script involved is the direction flag, which CSS cannot derive because no
selector can see where a navigation is headed.

Two platform constraints shape the implementation:

- **`view-transition-name` has no effect inside a shadow root.** Snapshot names are therefore
  applied in the document stylesheet to light-DOM hosts explicitly marked with `view-transition-name`,
  rather than to elements inside component layouts.
  The document root has `view-transition-name: none`, so the
  nav, footer, and persistent starfield remain live while named content snapshots travel above them.
- **A view transition captures the incoming element rather than showing it live**, and the element's own
  transform is baked into that capture. Both halves must therefore be driven from the
  `::view-transition-old()` and `::view-transition-new()` pseudo-elements; an animation declared on the real
  element is sampled once and never plays.

The element-level entrance that remains is for cold loads, where there is no outgoing page and so no
transition at all. It is scoped to `:root:not([data-nav-direction])` so it cannot also fire during a
navigation and compound with the pseudo-element animation.

## Code conventions and validation

Follow `.prettierrc.json`: tabs in code, single quotes, semicolons, trailing commas, and a 120-column width.
TypeScript is strict, including unchecked indexed access and exact optional properties. ESLint rejects
explicit `any`; use types that describe the data.

`src/result.ts` provides `Ok<T>`, `Err<E>`, `Result<T, E>`, `AsyncResult<T, E>`, `safeTry`, and
`asyncSafeTry`. Narrow the `ok` discriminant before reading a value or error.

### Testing foundation

Use the Node version declared in `package.json` (24.21 or newer). Node strips erasable TypeScript
syntax natively; unit tests need neither a loader nor a type-stripping flag. Their relative imports
include `.ts` extensions, enabled for typechecking by `allowImportingTsExtensions`. Keep `pnpm typecheck`
as a separate check because stripping types does not validate them.

After installing the locked dependencies, install the test browser once:

```sh
pnpm exec playwright install chromium
```

On Linux CI hosts without browser libraries, use `pnpm exec playwright install --with-deps chromium`.
An existing compatible Chrome installation can be used with `PLAYWRIGHT_CHANNEL=chrome pnpm test`.

- **Units:** `tests/unit/` uses native `node:test`. Coverage includes `src/result.ts`, `src/routes.ts`, and `src/orbit-gesture.ts`,
  with 100% line, branch, and function thresholds. Add pure modules to the coverage scope as they gain tests;
  this threshold describes the tested scope, not the whole application.
- **Components:** `stories/` and `.storybook/` use the Web Components/Vite framework. Storybook's Vitest
  addon runs stories and their `play` functions in real Chromium. The initial card stories check public
  slots, focusable controls, and responsive layout without opening closed shadow roots.
- **E2E:** `tests/e2e/` uses Playwright user stories, repeated on desktop and mobile viewports. The runner
  builds and starts the static site itself; stop any other server on port 4173 before running it. Stories
  cover direct destinations, persisted keyboard motion preferences, and breadcrumb/history navigation
  that preserves the background. Browser controls exercise closed-root components through normal clicks
  and keyboard input.

Unit coverage and component/E2E results print to the CLI. Playwright also writes a JSON report and keeps
traces only for failures in `.test-results/`. Generated coverage, reports, and `storybook-static/` are
ignored by Git. Keep unit tests focused on pure contracts and browser tests on observable behavior.

For code changes, run `pnpm test`, `pnpm typecheck`, `pnpm lint`, `pnpm format`, and `pnpm build`.
For Storybook changes, also run `pnpm build:storybook`. Report pre-existing failures separately from new ones. For UI or routing changes, also check the affected pages in a browser,
including a direct load and navigation from another page.
For documentation-only changes, check the text, referenced paths, and formatting. Avoid repository-wide
format fixes for a small edit. Do not commit `dist/`, `node_modules/`, or generated `*.tmp.*` files.
