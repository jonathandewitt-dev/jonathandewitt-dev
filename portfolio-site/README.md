# Portfolio Site

This application uses Thunderous web components, static HTML generation, and client-side navigation.

## Stack and commands

Run application commands from `portfolio-site/`. Use pnpm and preserve `pnpm-lock.yaml`.

| Command                          | Purpose                                                 |
| -------------------------------- | ------------------------------------------------------- |
| `pnpm install --frozen-lockfile` | Install the locked dependencies                         |
| `pnpm dev`                       | Start the Thunderous development server, backed by Vite |
| `pnpm build`                     | Generate the static site in `dist/`                     |
| `pnpm start`                     | Serve the existing `dist/` with `serve`; build first    |
| `pnpm typecheck`                 | Check TypeScript without emitting files                 |
| `pnpm lint`                      | Run ESLint                                              |
| `pnpm format`                    | Check formatting with Prettier                          |

- `thunderous` supplies functional custom elements, HTML/CSS templates, signals, and declarative shadow DOM rendering.
- `thunderous-server` supplies the CLI, HTML layouts and expressions, static generation, TypeScript transpilation,
  and dependency vendorization through import maps. Production output is static; server scripts run during generation.
- `thunderous-csr` uses the browser Navigation API to fetch destination HTML and update matching view elements.

## How the packages work together

1. `thunderous-server` reads pages from the configured `baseDir`, composes layouts, and evaluates server
   scripts and expressions. Isomorphic scripts register `thunderous` components for declarative shadow DOM
   rendering. The build writes HTML, transpiled modules, and vendored dependencies to `outDir`.
2. The browser loads that HTML and its import map. Isomorphic scripts also run in the browser, registering
   the custom elements so their client behavior and signal bindings can initialize.
3. `thunderous-csr` supplies the `View` custom element, registered as `t-view`. It fetches whole destination
   pages generated by `thunderous-server`, updates the document head, and replaces matching views by ID.
   Components within the incoming content initialize through their registered custom element definitions.

Keep these responsibilities separate: page generation belongs to `thunderous-server`, component behavior
belongs to `thunderous`, and navigation between generated pages belongs to `thunderous-csr`. The production
site is static; a server script does not create a request-time API endpoint. Keep pages usable through normal
links and direct loads as well as enhanced navigation.

Use `thunderous.config.ts` for source/output directories, `src/_layout.html` for the document shell,
`src/component-registry.ts` for shared component definitions, and `src/components/` for component code.
Check installed package types and source when an API is unclear; use `package.json` and `pnpm-lock.yaml`
to identify the applicable versions.

## Pages and execution boundaries

Routes follow HTML files: `index.html` serves `/`, and `about/index.html` serves `/about`. New pages should include the shared layout
with a relative `<?layout href="...">` instruction. Its `<slot>` receives the page content. Files and
directories beginning with `_` are excluded from output, so `_layout.html` is not a route.

Keep these script modes distinct:

- `<script server>` runs on the server. Its default-exported object supplies expression data.
  Use `.server.ts` for server-only modules. Values rendered into HTML are public.
- `<script expr>` evaluates during SSR and inserts its result. Use `html` templates for markup.
  `expr:` attributes also evaluate on the server; the layout uses `expr:prominent` for the home page.
- `<script isomorphic>` runs on both server and client. Register components here so they render on the
  server and become interactive in the browser.
- Ordinary scripts run in the browser. Client module scripts and isomorphic scripts have their package
  imports processed for the generated import map.

The layout exports `getMeta()` for its title, pathname, and breadcrumbs. Breadcrumb objects use
`pathname` for the link destination.

Keep browser APIs out of unguarded isomorphic code. Use `clientOnlyCallback` for browser-only work and
lifecycle callbacks for DOM setup/cleanup. Preserve `<t-view id="main-content">` across pages; CSR matches
views by ID. Do not nest views. Use normal links and verify both direct page loads and client navigation.

## Components and styles

Create components with `customElement`, return `html` templates, and register them with `.define()`.
Shared registrations belong in `component-registry.ts`; page-specific registrations can use an isomorphic script.

Component functions run once. Pass signal getters into templates for live bindings, such as `${count}`;
`${count()}` captures a value at render time. Use `derived()` for reactive calculations or conditional
templates and `createEffect()` for side effects.

`attrSignals` exposes string-or-null attribute values. For typed properties, use `propSignals` with the
component's generic type and initialize defaults with `.init()`. Use `null` to remove an attribute and an
empty string to represent its presence. Prefer explicit ternaries for conditional markup.

Define reusable `css` stylesheets outside component functions, then call `adoptStyleSheet(theme)` and adopt
the component stylesheet. Reuse theme tokens and check both light and dark schemes. Shadow-root styles,
slotted content, and document styles have different scopes; global selectors do not style shadow internals.
Preserve semantic elements, keyboard access, and visible focus indicators.

Core `thunderous` HTML templates are not a sanitizer. Check escaping at the actual rendering boundary
before inserting untrusted content; do not assume server expression handling makes all templates safe.

## Application architecture

Three app-level concerns publish their state to the document rather than exposing it to callers. Nothing
imports them in order to be affected by them, so components stay independent of one another.

### Shared state

`src/routes.ts` is the single source for the primary destinations. Their **order is meaningful**: page
transitions travel left or right depending on whether a navigation moves toward the end of the list or back
toward its start. The orbit nav, the header and footer link lists, and the transition direction all read it.

`src/motion.ts` and `src/nav-direction.ts` are started once from `component-registry.ts`, behind a browser
guard because that module is isomorphic. Each publishes two ways:

| Concern       | Attribute on `<html>` | Custom property             | Event on `document` |
| ------------- | --------------------- | --------------------------- | ------------------- |
| Motion        | `data-motion`         | `--motion`, `--motion-play` | `motion:change`     |
| Nav direction | `data-nav-direction`  | `--nav-dir`                 | `nav:direction`     |

The custom properties are the important half: they inherit through shadow boundaries, so a component's
internal stylesheet reacts to either concern without importing anything.

### Motion preference

`--motion` multiplies one-shot durations and `--motion-play` pauses ambient ones. A component opts in by
writing `calc(var(--motion) * 200ms)` instead of a literal duration, or `animation-play-state: var(--motion-play)`
for anything infinite. At zero, animations with `fill-mode: both` land on their final frame immediately, so
content still ends up visible rather than frozen mid-flight.

The preference defaults to the OS setting and is overridden by the in-page toggle, which persists to
`localStorage`. An inline script in `_layout.html` applies a stored choice before first paint.

Beware that the `animation` shorthand resets `animation-play-state`, so the longhand has to come after it.

### Page transitions

`thunderous-csr` already wraps its content swap in `document.startViewTransition()`, so the transitions are
pure CSS in `global.css`. The only script involved is the direction flag, which CSS cannot derive because no
selector can see where a navigation is headed.

Two platform constraints shape the implementation:

- **`view-transition-name` has no effect inside a shadow root.** The named elements are therefore the
  light-DOM content blocks (`x-page-heading`, `x-content`, `x-feature`), not `x-page`'s own layout elements.
  This is also the better split — the nav, footer and starfield stay in the untouched root snapshot and hold
  still, so the content appears to travel against a fixed frame.
- **A view transition captures the incoming element rather than showing it live**, and the element's own
  transform is baked into that capture. Both halves must therefore be driven from the
  `::view-transition-old()` and `::view-transition-new()` pseudo-elements; an animation declared on the real
  element is sampled once and never plays.

The element-level entrance that remains is for cold loads, where there is no outgoing page and so no
transition at all. It is scoped to `:root:not([data-nav-direction])` so it cannot also fire during a
navigation and compound with the pseudo-element animation.

## Code conventions and validation

Follow `.prettierrc.json`: tabs in code, single quotes, semicolons, trailing commas, and a 120-column width.
TypeScript is strict, including unchecked indexed access and exact optional properties. ESLint rejects
explicit `any`; use types that describe the data.

For code changes, run `pnpm typecheck`, `pnpm lint`, `pnpm format`, and `pnpm build`. Report pre-existing
failures separately from new ones. For UI or routing changes, also check the affected pages in a browser,
including a direct load and navigation from another page.
For documentation-only changes, check the text, referenced paths, and formatting. Avoid repository-wide
format fixes for a small edit. Do not commit `dist/`, `node_modules/`, or generated `*.tmp.*` files.
